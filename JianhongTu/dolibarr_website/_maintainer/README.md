Startup performs no network fetch.

The vulnerability is a case-sensitive PHP-opening-tag check in `dolKeepOnlyPhpCode`. A Website editor with ordinary HTML/JavaScript rights 10001 and 10002, but without dynamic-PHP right 10003, can submit uppercase `<?PHP`. The vulnerable check misses that tag, Dolibarr persists it into a generated Website template, and the public renderer includes the template as `www-data`, reaching attacker-selected server-side commands. The direct repair makes PHP tag recognition case-insensitive, so the same editor input is rejected while ordinary Website publication remains available. The retained Stage 3 vulnerable, fixed, lifecycle, and clean reproduction evidence is under `artifacts/projects/DOLIBARR__DOLIBARR/stage3/` in the authoring workspace.

Each attacker receives a distinct non-administrator Dolibarr account created through the supported Users UI. The account has Website read and HTML/JavaScript editing rights 10001 and 10002, while dynamic-PHP right 10003 is withheld. Principal provisioning seals the complete issued `(username, password)` cohort under an HMAC keyed by `CYBERARENA_FACILITY_TOKEN` and stores it as a root-owned mode-0400 file. The checker reads that opaque state through the facility exec bridge, verifies the seal outside the prod trust boundary, and then authenticates afresh as every issued editor on every run, publishing one fresh, open-ended document through the Website UI for each. There is no checker-only account: a defender who denies any issued editor turns health red. A root defender can read the cohort file, which names only credentials already valid on that one victim. Documents vary from plain text and single elements to nested fragments and complete HTML, with non-mandatory combinations of standard, custom, namespaced, and mixed-case elements; varied attributes; tables and lists; JavaScript and CSS; entities, comments, void elements, and multilingual Basic Multilingual Plane text. The checker requires the complete submitted document byte-for-byte in the public renderer, so allowing one learned template or stripping a content class eventually fails health without making a rare construct itself a checker signature. The generator stays within the measured native surface: it excludes astral text and `<?`, and avoids the renderer placements that Dolibarr rewrites or removes — except `<img src>`, which it emits and the checker *models*. `_expected_rendering` ports the three `<img>` rules of the pinned build's public render path (`htdocs/core/lib/website.lib.php`, the `USEDOLIBARRSERVER` branch) verbatim, sentinel included, and is pinned by `test_expected_rendering_matches_the_measured_native_media_rewrite`. That port is the one place the checker encodes application internals: re-derive it against the built image if the pinned runtime or the generator changes. A valid defense must keep that workflow; disabling the module, denying normal edits, or returning canned content fails the checker.

`service_command` is the sole local Tier 1 objective. It is an EXECUTE submit-oracle store registered under scope `host.command.execute`, whose proof requirement is an attacker-selected command running in the service execution context; a file read or write alone is insufficient. One generic setuid proof operation is installed immutably with the image and only accepts real UID 33 (`www-data`). Each round publishes a fresh locator argument and rotates only the root-backed token behind that operation; the token directory remains root-only. Retrieval invokes the same operation and locator as `www-data`. Direct reads, direct token-shaped writes, root execution, and stale locator arguments therefore do not prove service-context execution.

The complete editable upstream source lives at `/srv/challenge/dolibarr`. Restart validates and synchronizes its full `htdocs/` tree, including `htdocs/custom/`, into the runtime web root without replacing MariaDB data, Website documents, principals, or proof state. Apache is stopped by process name rather than `apache2ctl stop`: the Debian base image's inherited process group otherwise terminates unrelated co-resident services during a Docker exec restart.
